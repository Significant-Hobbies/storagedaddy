# StorageDaddy 0.1.4 qualification

Startup accounting separates occupied APFS capacity, scanned allocated files,
used space outside the breakdown, free space, named system volumes and signed
pool adjustments. Unreadable folders show unknown coverage rather than empty
sizes. Folder recognition supplies tailored explanations for source projects,
dependencies, builds, caches, models, persistent VM stores and personal data.
Recognition does not establish abandonment, inactivity or safe deletion.

Issues #33–38 reuse the Map & inspector direction selected on #33 and the
reviewed source prepared in PR #50. The map provides independent kind colors,
candidate hatching, explicit staging, file-entry area, dimmed name filters,
project Git evidence and an upper-bound free-space projection. Duplicates run
only on request, require full content equality and protect kept copies from
direct or ancestor cleanup. Projects preserve workspace roots and block recent,
incomplete, linked, key-containing, Git-tracked or unverified artifacts. A
user-reviewed recovery plan is separate from selection; final confirmation
revalidates project evidence and the normal cleanup preflight.

App Data compares bounded standard-folder app references with direct Library
roots. Missing ownership is unverified; partial references offer no absence
candidates. Existing installer and old-Download candidates remain deliberate
review items. File Types groups actual files; Age Map adds monthly, quarterly
and yearly histograms plus byte-weighted age percentiles. Dates describe
modifications rather than last use. The optional interval filter and optional
historical SMART trend are outside this release's required scope.

The dashboard reports inode availability and two-sample physical-driver and
APFS-volume block I/O separately. Volume traffic uses exact IORegistry BSD name,
entry identity and boot identity. Missing counters, resets and mounted snapshot
names without an exact counter remain unavailable. Pseudo-filesystem inode
sentinels are unknown. The documented readiness heuristic withholds its total
until all four associated inputs are measured; it is not a drive diagnosis.

Issue #48 adds the published App Health Swift SDK at exact tag 0.1.0. It is off
without a valid per-user native public key; no key is bundled or configured.
Only foreground-session heartbeats are admitted. Lifecycle transitions are
ordered, backgrounding stops heartbeats and termination calls close with a
three-second quit bound. Tests use fake clients/transports. Privacy disclosure
and MIT notices are included. Owner-created-key live acceptance remains a
separate action, as specified by the issue; native usage stays unmeasured until
that runtime receipt exists.

Local qualification: the complete Swift suite, optimized native build,
Sparkle helper tests, staged-byte appcast parity/rejection checks, 17 site tests,
TypeScript and Wrangler dry-run passed. Native controlled-folder QA exercised
map/inspector, duplicate survivor staging, separate cleanup confirmation and
Cancel, project protection/recovery-plan Cancel, partial app-reference handling,
all age intervals, File Types and live per-volume I/O. Both duplicate fixture
files remained intact; no Trash operation or physical space recovery is claimed.
Native renders cover the 880-point minimum plus larger widths; full-shell
synthetic checks also cover 880×600. The v2 preservation review passed. Signing,
notarization, public feed/download parity and installed update acceptance are
separate protected-release gates, recorded by the release workflow and runtime
qualification.

Full Disk Access is optional and must be granted by the owner. Without it,
protected file-level attribution remains incomplete even when total APFS used
space is reconciled and explained.
